# Convoy – live tracking for road trips with more than one vehicle

A mobile-first **website** (nothing to install) that shows every vehicle in a group on one live map, works out who is ahead and who is behind **along the planned route**, and warns the group when someone falls behind, takes a wrong turn or stops.

Stack: React + Vite + Tailwind + Lucide · Leaflet + OpenStreetMap · Node + Express · Socket.IO · MongoDB · browser Geolocation API.

---

## 1. Quick start (local)

Requires **Node 20+** (22 recommended) and **MongoDB** (local, or a free MongoDB Atlas cluster).

```bash
# 1. Database (pick one)
docker run -d --name convoy-mongo -p 27017:27017 mongo:7
#    ...or create a free Atlas cluster and put its connection string in MONGODB_URI below

# 2. Install everything
npm run setup

# 3. Configure the server
cp server/.env.example server/.env
#    edit server/.env: set JWT_SECRET (instructions inside), and MONGODB_URI if not local

# 4. Run (two terminals)
npm run dev:server      # API + realtime on http://localhost:4000
npm run dev:client      # website on  http://localhost:5173
```

Open http://localhost:5173, create a journey, then open the invite link in a second (incognito) window to join as another vehicle.

**Try everything without driving:** as Journey Leader open the **Leader** tab, then **Testing mode**, then *Start testing mode*. Seven clearly labelled **SIM** vehicles drive your real planned route: one overtakes, one slows down and falls behind, one takes a wrong turn, one stops, one drops its connection. Tip: set max separation to 2 km and the stopped alert to 1 minute to see those alerts sooner.

### Testing GPS on a phone
Browsers only allow GPS on **HTTPS** (or `localhost`). A phone opening `http://192.168.x.x:5173` gets the map but **not** GPS. Use a tunnel such as `npx cloudflared tunnel --url http://localhost:5173` (or ngrok), or deploy (section 8). Set `CLIENT_ORIGIN` in `server/.env` to the HTTPS address you use so invite links and QR codes point to it.

## 2. What is built

| Area | Details |
|---|---|
| Landing | Navigation, hero, How it works, Features, Why, Safety and privacy, footer |
| Create / join | Create journey: unique ID, 6-character join code, QR code, share link. Join by code, link or QR with just name and vehicle (no registration). Codes expire (48 h default) and can be paused or regenerated by the leader |
| Live map | Leaflet map (OpenStreetMap data, CARTO Voyager style) with planned route, start and destination; one icon, colour and name per vehicle; live updates over Socket.IO (no refresh); zoom and pan; **My vehicle** and **Show everyone** buttons; vehicles that stop reporting are drawn grey and dashed at their last known position |
| Consent | Explicit consent dialog, then the browser's own permission prompt. Visible *Sharing* banner with last-sent time and GPS accuracy; **Stop sharing** any time; sharing stops on leave or end |
| Vehicle order | Each GPS fix is snapped to the planned route and vehicles are ranked by **progress along the route**, never by raw latitude/longitude. If the order can't be trusted it says so instead of guessing |
| Distances | Between consecutive vehicles, to the vehicle ahead/behind you, and total group separation. **By route** (along the road) and **straight line** are always labelled separately |
| Separation alerts | Leader sets the maximum; alert when exceeded for 20 s; clears with hysteresis; shown to everyone |
| Route deviation | Threshold scales with GPS accuracy (minimum 150 m), must last 15 s, ignored on poor accuracy and in the first/last 300 m; shows last known location |
| Vehicle status | Moving, Stopped, Location unavailable, Disconnected. "Stopped for N minutes" alert (configurable); a GPS dropout resets the timer so it is never read as stopping; no stop alert at the destination |
| SOS | Confirmation step, then a critical alert to the whole group with the latest location and its age. States clearly that it does **not** contact emergency services |
| Leader tools | Invite, max separation, stop-alert time, change destination (re-routes), retry route, remove participants, end journey, testing mode |
| Journey info | Name, start, destination, vehicle count, total/travelled/remaining distance, ETA (estimate), journey time, progress bar |
| Responsive | Phones: full-screen map, a one-glance vehicle carousel and a draggable bottom sheet with slim expandable rows. Tablets and desktop: side panel plus map. Compact type scale, 44 px touch targets, icon-and-text status, visible keyboard focus, reduced motion respected |

## 3. Honest limitations (please read)

* **Browsers can pause GPS when the app is in the background or the screen locks.** This is a limit of every website, not just Convoy. Convoy does the most a website can (see "Switching apps" below), but some phones, especially with battery saver on, may still pause it. The vehicle is then shown as **stale or unavailable with its last-update time**, never as live.
* **HTTPS is required** for GPS on phones.
* **SOS only notifies people in the journey**, over the internet, using the last GPS fix. It does not call anyone.
* **Order accuracy** depends on GPS quality and a sensible route. Vehicles that are off-route or have poor accuracy are left out of the order and listed separately.
* **Free routing and map services have limits.** Without `ORS_API_KEY` the server uses OpenStreetMap's Nominatim and the public OSRM demo server (fine for development and small groups, not heavy traffic). For production add a free OpenRouteService key. The map uses CARTO's free "Voyager" tiles (OpenStreetMap data) for a cleaner look; for production traffic use your own tile provider or account by setting `VITE_TILE_URL` and `VITE_TILE_ATTRIBUTION` (see `client/.env.example`).
* Changing the destination re-routes from the original start point.
* Alerts are held in memory and rebuilt from live data after a server restart. Live positions are cleared when a journey ends; location history is deleted after 7 days.

## 3a. Switching apps (background sharing)

A website cannot run GPS in the background the way a native app can, but Convoy does everything a website is allowed to:

* **Keep-alive while sharing:** a silent audio loop plus a screen wake lock tell the phone the page is in active use. A "Sharing your location" media control appears in the notification shade / lock screen; pausing it **stops sharing**, so it is always visible and always under your control.
* **Instant recovery:** the moment you return to Convoy (or the network comes back) it restarts GPS and sends a fresh fix; a GPS watch that goes quiet is restarted automatically.
* **Resume after the phone discards the tab:** if sharing was on and the browser permission is still granted, sharing resumes on its own when you reopen the page.
* **Install it:** "Add to Home Screen" (Chrome menu on Android, Share menu on iPhone) opens Convoy as its own app window, which phones are less likely to freeze.
* **Honest status:** if updates stop anyway, everyone sees that vehicle as stale with its last-update time.

Tips for reliable sharing: keep Convoy on screen when you can, turn off battery saver for your browser, and allow location "always while using the app".

## 4. How vehicle order works

```
GPS fix --> snap to planned route --> progress (metres from start) + distance from route
              |
   live? accuracy <= 200 m? within deviation threshold?  -- no --> "not in the order" with the reason
              | yes
   sort by progress (30 m hysteresis so GPS wobble doesn't flip the order)
              v
   rank, gap to vehicle ahead (route + straight line), gap to leader, group separation
```

Snapping uses the previous progress as a hint, so a route that loops back near itself doesn't make a vehicle jump to the wrong stretch. A unit test proves the order follows route progress even when the leading vehicle has a *lower latitude* than the one behind it (a U-shaped route).

## 5. Data model (MongoDB / Mongoose)

| Collection | Key fields |
|---|---|
| `journeys` | `journeyId` (public 12-char id), `name`, `start` and `destination` `{label, resolved, lat, lng}`, `journeyDate`, `status` (planned/active/ended), `leaderVehicleId`, `joinCode` (unique), `joinEnabled`, `joinCodeExpiresAt`, `maxSeparationKm`, `stopAlertMinutes`, `route {coordinates, distanceMeters, durationSeconds}`, `routeStatus`/`routeError`, `startedAt`, `endedAt` |
| `vehicles` | `journeyRef`, `vehicleName`, `vehicleType`, `driverName`, `color`, `isLeader`, `removed`, `sharingStatus`, `currentLocation`, `lastUpdatedAt`, `simulated`, `sos` |
| `locationpoints` | `vehicleRef`, `journeyRef`, `lat`, `lng`, `speed`, `accuracy`, `timestamp`; **auto-deleted after 7 days** (TTL index) |

There are no user accounts: joining creates a vehicle record and a signed 14-day token tied to that one journey and vehicle. Indexes are created automatically on first start.

## 6. API and realtime events

REST (`/api/journeys...`): `POST /` create, `GET /preview/:code`, `POST /join`, `GET /:id`, `POST /:id/code/regenerate`, `POST /:id/code/enabled`, `POST /:id/leave`. Leader only: `PATCH /:id/settings`, `POST /:id/destination`, `POST /:id/route/retry`, `DELETE /:id/members/:vehicleId`, `POST /:id/end`.

Socket.IO (authenticated with the member token; only members join a journey's room):
client to server: `location:update`, `sharing:stop`, `sharing:denied`, `sos:start`, `sos:cancel`, `sim:start`, `sim:stop` (leader);
server to client: `init`, `state` (every 2 s), `alert`, `route`, `journey:ended`, `removed`.

**Security:** zod validation on all REST bodies and socket payloads; per-journey authorisation on every request and socket; rate limits (general, code guessing, journey creation, location updates); Helmet headers; secrets only in environment variables; locations are never public and never returned by REST; ending a journey wipes live positions.

## 8. Deployment (one service, HTTPS included)

The server also serves the built website, so one host is enough.

1. **Database:** create a free MongoDB Atlas cluster, allow your host's IPs, copy the connection string.
2. **Host (Render, Railway or Fly.io):** create a Node web service from this repo.
   * Build command: `npm run setup && npm run build`
   * Start command: `npm start`
   * Environment: `NODE_ENV=production`, `MONGODB_URI`, `JWT_SECRET`, `CLIENT_ORIGIN=https://your-site-url`, and either `NOMINATIM_USER_AGENT` (your email) or `ORS_API_KEY`. Testing mode is off in production unless you set `ALLOW_SIMULATION=true`.
3. Open the HTTPS URL on a phone. WebSockets work on these hosts without extra configuration.

**Routing key:** get a free key at https://openrouteservice.org and put it in `ORS_API_KEY`. Only the server ever uses it.

**Separate hosting (optional):** host `client/dist` on Netlify or Vercel with a rewrite of all paths to `index.html`, build with `VITE_API_URL=https://your-api`, and on the server set `SERVE_CLIENT=false` and `CLIENT_ORIGIN` to the site URL.
